## The Reasoning

Per onboarding event the domain work is four null checks; a Discord REST call is 50–500 ms of network. The workload is essentially 100% I/O, and the ceiling is Discord's rate limits — **per bot token, not per thread**. Roughly 50 req/s global, bucketed per route.

Reconciling a 10,000-member guild is 10,000 role calls, which is 20–30 minutes of wall clock no matter how many threads run. Extra threads would contend for the same bucket and produce more 429s, while needing cross-thread rate-limit coordination that discord.js gives free inside one process. `better-sqlite3` is synchronous and does not take concurrent writers across threads either.

So the answer is process-level sharding (which Discord mandates past 2,500 guilds anyway) plus concurrency control, not threads.

## Real Optimisations Found

- **Both repositories called `db.prepare()` on every invocation**, recompiling SQL each time. `get`/`getAnswers` run on effectively every gateway event — this was the hottest avoidable cost in the process. Now compiled once at construction, transactions included
- **`listAwaitingReminder` filtered elapsed time in JavaScript**, deserialising every pending row in every guild each sweep. Moved into SQL with a `LIMIT`
- **Guild config was read from SQLite on every event.** Now a `Map` lookup behind a read-through cache, invalidated per guild on write
- **discord.js default caches** retain messages, presences and users indefinitely — the dominant memory cost across thousands of guilds, and worth nothing to this bot. Disabled and swept
- **Reconciliation had no yield boundary and no ceiling**; a 50k-member guild would hold the event loop for the whole backfill. Now chunked at 200 with a yield between chunks
- Guilds reconcile **sequentially** — they share one rate-limit budget, so parallelism only deepens the queue

## Decisions Made

- No `worker_threads` anywhere; plan 05 acceptance criteria asserts the absence
- One queue, two priorities. Interactive is never rejected; only bulk is, past `maxQueued`
- A full queue surfaces as a failed `Result`, not a throw — the next reconciliation recovers it
- Sharding uses `mode: 'process'` so each shard gets its own event loop and heap
- SQLite stays; write volume is ~1/sec at 1,000 active guilds. Postgres swap point is documented, triggered by write contention in the lag metric
- Grandfathering turns out to be a performance decision as well as a safety one — it removes the largest possible bulk workload from the critical path
